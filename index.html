      How it works
      
We protect at the layer the reader actually sees.

      
The attacker never reads your binary — they read the decompiler's output. So Murkwire shapes that output: valid for the runtime, hostile to anything trying to understand it. Depth depends on how your language ships.

      What it does
      
Five transforms, aimed at comprehension — not just copying.

      
Classic obfuscators rename things and stop. Murkwire targets the signals a model leans on to understand code, applied surgically to the methods that matter so runtime cost stays low.

    

    

      

        
        
Irreducible control flow

        
Jump graphs the JVM runs happily but that don't map to any if/while. Decompilers emit a maze of state variables; models lose the thread.

      

      

        
        
String encryption

        
Literals are a model's main semantic anchor. Encrypted and decrypted at runtime, they leave the decompiled output with no readable clue about intent.

      

      

        
        
Reflection indirection

        
Direct calls become reflective lookups. The call graph — half of what makes code understandable — dissolves for both tools and models.

      

      

        
        
Decompiler crashers

        
Bytecode patterns tuned to each tool's known failure modes — making CFR, Procyon or Jadx emit garbage, or refuse to decompile at all.

      

      

        
        
Misleading metadata

        
Synthetic local names and line tables that actively suggest the wrong behavior, so a skim read leads the reverse-engineer away from the truth.

      

      

        
        
The anti-LLM harness

        
Every build is scored by running protected output through real models and measuring how much comprehension drops. That number is the product — not a guess.

      Drops into your build
      
One line in CI. Nothing else changes.

      
Murkwire runs as a post-compile step inside the pipeline you already have. No source changes, no new build system, no source leaving your walls.

    

    


# build.gradle.kts
plugins {
  id("dev.murkwire.protect") version "1.4.0"
}

murkwire {
  profile  = "antiLLM.aggressive"   // transform preset
  target   = "**/payments/**"      // protect what matters
  report   = true                   // emit Comprehension Score
}

$ ./gradlew build
  → compiling… done
  → murkwire: 34 classes hardened · CCS 91 → 9
  → artifact written · runtime overhead +3.1%

      Straight answers
      
Questions worth asking first.

    

    

      
Isn't obfuscation a solved, defeated thing? +
Renaming variables is, and modern models undo it easily. Murkwire's value is in the structural transforms — irreducible control flow and decompiler crashers degrade a model's understanding, not just a human's. It's a cost multiplier, never an absolute wall, and we're explicit about that.

      
Will it slow my code down or break my stack traces? +
Heavy transforms carry real cost, which is why Murkwire is per-method: you protect the logic that matters and leave the rest untouched. Typical runtime overhead lands in the low single digits. Murkwire also emits a mapping file so you can de-obfuscate your own crash reports.

      
Can't someone just feed the raw bytecode to a model? +
They can try, and models do reason over bytecode somewhat — which is exactly why we score against that path too, not only against decompiled output. No protection is total. The honest claim is that Murkwire makes understanding your code slow and expensive enough that most attackers move on.

      
Does my source code go to your servers? +
No. Murkwire runs as a step inside your own CI, on your infrastructure. Enterprise runs fully air-gapped. We never see your code, and that's a selling point for the banks and studios we built this for.

      
What does Murkwire refuse to do? +
It protects your code; it doesn't weaponize it. Murkwire will not inject payloads that hijack someone's AI assistant or attack whoever reads your artifact — that targets third parties, carries legal and reputational risk, and isn't something a serious buyer wants shipped in their software. Defense only.
